## Структура БД

### 1️⃣ Таблица `users` (Пользователи)

Хранит профиль, цели и параметры времени.

| Поле | Тип данных (SQL) | Описание / Назначение |
| --- | --- | --- |
| **`id`** | `BIGINT` (Primary Key) | Telegram ID пользователя (`message.from_user.id`) |
| **`first_name`** | `VARCHAR(100)` | Имя пользователя |
| **`gender`** | `VARCHAR(10)` | `'male'` / `'female'` |
| **`age`** | `INT` | Возраст (для расчёта нормы ккал) |
| **`height`** | `FLOAT` | Рост в см |
| **`weight`** | `FLOAT` | Вес в кг |
| **`activity_level`** | `FLOAT` | Коэффициент активности (1.2, 1.375, 1.55 и т.д.) |
| **`goal`** | `VARCHAR(20)` | `'weight_loss'`, `'muscle_gain'`, `'maintain'` |
| **`daily_calories`** | `INT` | Целевая суточная норма ккал |
| **`timezone`** | `VARCHAR(50)` | Часовой пояс IANA (например, `'Europe/Moscow'`) |
| **`day_change_hour`** | `INT` (Default: `4`) | Час смены суток (по умолчанию `4` = 04:00 утра) |
| **`last_active_at`** | `BIGINT` (Unix Time) | Время последней активности (для заморозки через 3 дня) |
| **`created_at`** | `BIGINT` (Unix Time) | Дата и время регистрации |

---

### 2️⃣ Таблица `food_logs` (Записи дневника питания)

Хранит **подтверждённые** приёмы пищи. Поля `title`, `calories`, `proteins`, `fats`, `carbs`, `portion_g` напрямую соответствуют полям из `FoodResult`.

| Поле | Тип данных (SQL) | Описание / Назначение |
| --- | --- | --- |
| **`id`** | `BIGINT` (Primary Key) | Авто-инкрементный ID записи |
| **`user_id`** | `BIGINT` (Foreign Key) | Ссылка на `users.id` |
| **`title`** | `VARCHAR(255)` | Из `FoodResult.dish` (Название блюда / «Приём пищи») |
| **`calories`** | `INT` | Из `FoodResult.calories` (Калории, ккал) |
| **`proteins`** | `FLOAT` | Из `FoodResult.proteins` (Белки, г) |
| **`fats`** | `FLOAT` | Из `FoodResult.fats` (Жиры, г) |
| **`carbs`** | `FLOAT` | Из `FoodResult.carbs` (Углеводы, г) |
| **`portion_g`** | `FLOAT` | Из `FoodResult.portion_g` (Вес порции, г) |
| **`logged_date`** | `VARCHAR(10)` | Логическая дата `YYYY-MM-DD` с учётом сдвига 04:00 |
| **`created_at`** | `BIGINT` (Unix Time) | Точный Timestamp добавления записи |
| **`details_json`** | `JSONB` / `TEXT` | Сырой JSON ответа Gemini (`FoodResult.model_dump_json()`) |

> ⚡ **Составной индекс (Индексация):**
> `CREATE INDEX idx_food_logs_user_date ON food_logs (user_id, logged_date);`
> *Обеспечивает мгновенную отдачу дневника за конкретный день через `WHERE user_id = X AND logged_date = 'YYYY-MM-DD'`.*

---

### 3️⃣ Таблица `reminders` (Напоминания / Витамины)

Хранит настроенные окна напоминаний перед едой.

| Поле | Тип данных (SQL) | Описание / Назначение |
| --- | --- | --- |
| **`id`** | `BIGINT` (Primary Key) | Авто-инкрементный ID напоминания |
| **`user_id`** | `BIGINT` (Foreign Key) | Ссылка на `users.id` |
| **`title`** | `VARCHAR(255)` | Текст напоминания (например, «Выпить Омега-3») |
| **`time_start`** | `VARCHAR(5)` | Начало окна, например `'12:00'` |
| **`time_end`** | `VARCHAR(5)` | Конец окна, например `'15:00'` |
| **`min_calories`** | `INT` (Default: `0`) | `0` — реагировать на любую еду, `>=250` — только на крупный приём |
| **`is_triggered_today`** | `BOOLEAN` (Default: `False`) | Флаг: срабатывало ли уже напоминание за текущие сутки |
| **`is_active`** | `BOOLEAN` (Default: `True`) | Включено/выключено пользователем |

---

### Как это работает во FSM (`FoodFlow`)

1. **Распознавание:** Пользователь кидает фото/текст → Gemini отдаёт объект `FoodResult`.
2. **Состояние `FoodFlow.confirming`:** Данные временно хранятся в FSM-контексте (`state.update_data(...)`).
3. **Подтверждение:** Если пользователь соглашается (или срабатывает автоподтверждение по таймеру), данные переносятся из FSM-контекста прямо в SQL-таблицу `food_logs`.
4. **Триггер напоминаний:** После вставки записи в `food_logs` выполняется проверка таблицы `reminders`: если текущее время попадает в окно `time_start..time_end` и `calories >= min_calories`, бот выдаёт уведомление о витаминах.

## Как будем хранить дату приёмов пищи:

## 1. Как доставать данные за кастомный день без тормозов?

### Проблема Unix Timestamp и смещения 04:00

Если день у пользователя меняется в `04:00`, а не в `00:00`, то логический день $D$ длится с $04:00$ дня $D$ до $03:59:59$ дня $D+1$.

Если хранить только точное время создания записи (например, Unix Timestamp `created_at = 1719543600`), то при каждом запросе дневника тебе пришлось бы выполнять вычисления времени на лету с учётом часового пояса и сдвига на 4 часа. В SQL это писать громоздко, а без специальных индексов база будет «чесать» всю таблицу (Full Table Scan).

### 🎁 Простая и реактивная математика (Решение)

При сохранении блюда бот **заранее знает**, к какому «логическому дню» относится запись.

Добавим в таблицу с едой **два поля**:

1. `created_at` — точный Unix Timestamp (нужен для сортировки внутри дня и показа времени, например `14:30`).
2. `logged_date` — логическая дата в формате `YYYY-MM-DD` (строка или тип DATE).

**Как считается `logged_date` в Python при сохранении:**

Python

```
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

def get_logical_date(user_now: datetime, day_start_hour: int = 4) -> str:
    # Если сейчас, например, 02:30 ночи 27 июля,
    # то отнимаем 4 часа -> получается 22:30 26 июля.
    # Значит, прием пищи относится к логическому дню "2026-07-26"!
    adjusted_time = user_now - timedelta(hours=day_start_hour)
    return adjusted_time.strftime("%Y-%m-%d")
```

### Почему это ЛЕТИТ по скорости?

Когда пользователь нажимает `[ ◀️ Вчера ]`, бот делает максимально простой и мгновенный SQL-запрос:

SQL

```
SELECT * FROM food_logs 
WHERE user_id = 123456789 
  AND logged_date = '2026-07-25' 
ORDER BY created_at ASC;
```

> **🔥 Секрет производительности (Индексы):**
>
> Чтобы база данных не тормозила даже при миллионах записей, мы повесим **составной индекс** `(user_id, logged_date)`.
>
> Поиск по такому индексу занимает **меньше 1 миллисекунды**, так как база мгновенно переходит к нужным записям пользователя за конкретную дату!
